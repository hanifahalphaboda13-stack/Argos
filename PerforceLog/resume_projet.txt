RÉSUMÉ DU PROJET — Détection d'antipatterns Perforce / BeepBeep
Date : 19 juin 2026 (mis à jour)
================================================================================

OBJECTIF DU PROJET
------------------
Détecter des antipatterns — définis ici comme des **mauvais comportements**
observables dans les logs Perforce — avec BeepBeep. Contexte : dépôt de jeux
(Unreal Engine 5.6) où Perforce versionne surtout des **fichiers binaires**
(.uasset, .umap, etc.) : l'analyse porte sur les métadonnées VCS (commandes,
chemins, timing), pas le contenu des assets. Le catalogue ReliSA en recense
168 ; nos traces n'en permettent d'exploiter qu'un sous-ensemble lié au cycle
edit / sync / submit / revert.


1. PÉRIMÈTRE DÉFINI (réunion superviseurs)
------------------------------------------

5 comportements retenus (sur 168 fiches ReliSA) — ceux détectables dans p4d :
  - Collective Procrastination (rush de submits)
  - Warm Bodies (devs peu actifs)
  - Lone Wolf (beaucoup d'edits, peu de submits)
  - Bystander Apathy (checkout sans submit)
  - Edit puis revert (checkout abandonné sans modification)

Commandes Perforce retenues (11) :
  user-edit, user-submit, user-sync, user-add, user-revert, user-lock,
  user-shelve, user-resolve, user-delete, user-diff, user-integrate

Référence : catalogue ReliSA — 168 antipatterns (sous-ensemble VCS seulement)
  https://github.com/ReliSA/Software-process-antipatterns-catalogue

Hors périmètre log Perforce (exemples) : réunions improductives, management,
spécifications floues, dette documentaire — nécessitent d'autres sources.

2. PARSEUR DE LOGS (LecteurLog.java, MetriquesServeur.java)
-----------------------------------------------------------

  - Lecture en streaming ; assemblage en blocs (cmd + completed + métriques ---)
  - 11 commandes user-* retenues
  - Extrait par bloc événement : timestamp, pid, user, workspace, ip, client,
    commande, args, fichiers, durée (completed), métriques serveur
  - Métriques après completed : lapse, memory, rpc, db locks, rows
  - Gère chemins Windows avec espaces et fichiers multiples
  - Associe durée + métriques via pid + ligne completed
  - Lecteur avec remise (pile) pour ne pas perdre d'événements


3. MODÈLE ET EXPORT (PerforceEvent, EnrichissementEvenements)
--------------------------------------------------------------

  - Fichiers en liste dans PerforceEvent ; args conservés séparément
  - Export principal aligné sur perforce_events_v3 (dataset de référence)
  - Export v3 (json/csv) et analyses BeepBeep sur événements sans doublons
  - Clé dédup : timestamp|pid|commande|args|fichiers
  - Affichage console : 20 premiers événements (format LigneAnalytique)


3b. COLONNES DE L'EXPORT (perforce_events_v3.json / .csv)
---------------------------------------------------------

  1 enregistrement par bloc événement assemblé (cmd + completed + ---).

  Colonnes (27) :
    timestamp, date, time, pid, user, workspace, ip, client, command, args,
    file_path, nb_files, project, file_ext,
    duration_s, lapse_s, mem_cmd_mb, mem_proc_mb,
    rpc_in, rpc_out, db_read_locks, db_write_locks,
    rows_get, rows_pos, rows_scan, rows_put, rows_del

  file_path : tableau JSON ["chemin1","chemin2"] ou chaîne CSV équivalente
  nb_files  : nombre de fichiers de l'événement
  file_ext  : extension(s) distincte(s) — une valeur ou tableau JSON ["uasset","umap"]
  project   : heuristique NAD/NAND, UE_X.X, dossier avant Content, etc.

  Heuristique project :
    - Dossier 20XX_NAD_* ou 20XX_NANDxxx_Nxx_Equipexx
    - Version UE (UE_5.6…)
    - Premier dossier après lecteur (ex. Enseignement)
    - Dossier parent avant /Content/
    - Segment dépôt //...
    - Vide si pas de fichier (ex. user-submit -i)


4. STRUCTURE DU PROJET (9 fichiers Java)
-----------------------------------------

  Main.java                    → Point d'entrée, exports
  LecteurLog.java              → Parse le log brut
  PerforceEvent.java           → Modèle d'événement
  MetriquesServeur.java        → Métriques --- après completed
  MetriquesPrometheus.java     → Noms métriques OpenMetrics (_total, _seconds)
  EnrichissementEvenements.java → Export v3 + affichage console
  UtilEvenements.java          → Doublons, BeepBeep phase 1 et 2, alertes
  HistogrammeDurees.java       → Buckets OpenMetrics (Histogram)
  SummaryDurees.java           → Quantiles p50/p90/p95/p99 (Summary)
  GenererGraphiques.java       → Figures PNG JFreeChart (dossier figures/)


5. PHASE 1 — MÉTRIQUES PROMETHEUS / OPENMETRICS AVEC BEEPBEEP (terminée)
--------------------------------------------------------------------------

Référence : client Java Prometheus (norme OpenMetrics)
  https://prometheus.github.io/client_java/

Types OpenMetrics et notre implémentation :

  Counter (implémenté)
    - Noms : perforce_events_total, perforce_user_submit_total, perforce_user_edit_total
    - Export : perforce_counters.json (help + value)

  Gauge (implémenté)
    - Noms : perforce_open_edit_files, perforce_open_edit_users
    - Export : perforce_gauges.json

  Histogram (implémenté)
    - perforce_command_duration_seconds (unit: seconds, help)
    - Labels : command (par_commande dans JSON)

  Summary (implémenté)
    - perforce_command_duration_seconds + quantiles 0.5/0.9/0.95/0.99
    - Batch exact (≠ fenêtre glissante client Java live)

  Référence nommage : MetriquesPrometheus.java (aligné client Java Prometheus)

  Info / StateSet / GaugeHistogram — hors scope

  Phase 2 (CEP) — hors types OpenMetrics
    - edit→revert, apathy, rush multi-users

6. PHASE 2 — PATTERNS TEMPORELS CEP AVEC BEEPBEEP (terminée)
-------------------------------------------------------------

Pipeline : QueueSource → FilterOn(edit/submit/revert) → détecteur d'état

Patterns :
  - Bystander Apathy : edit sans submit sur le fichier
  - Edit → revert : edit puis revert (même fichier)
  - Rush collectif : ≥ N users distincts submit / heure

Résultats (même run, événements dédupliqués) :
  Edit → revert     : 217 alertes
  Bystander Apathy  : 250 fichiers (cohérent avec gauge fin = 250)
  Rush collectif (≥ 3 users/heure) : 27/04 13h → 60 users, etc.

Export : perforce_events_alertes.json


7. COMPARAISON PHASE 1 vs PHASE 2
----------------------------------

  Antipattern                  | Phase 1 (Prometheus)     | Phase 2 (CEP)
  -----------------------------|--------------------------|---------------------------
  Procrastination collective   | Submits / heure          | N users distincts / heure
  Warm Bodies                  | Top/bottom activité      | —
  Lone Wolf                    | Ratio edit/submit        | —
  Bystander Apathy             | Gauge (fichiers ouverts) | edit sans submit
  Edit → revert                | —                        | edit puis revert


8. UTILISATION
--------------

  Prérequis : Java 11+ ; lib/beepbeep-3.13.jar, lib/jfreechart-1.0.19.jar, lib/jcommon-1.0.23.jar

  Compilation (depuis la racine du projet) :
    javac -cp "lib/beepbeep-3.13.jar:lib/jfreechart-1.0.19.jar:lib/jcommon-1.0.23.jar" \
          -d bin -sourcepath src src/ca/uqac/detection/*.java

  Exécution :
    java -cp "bin:lib/beepbeep-3.13.jar:lib/jfreechart-1.0.19.jar:lib/jcommon-1.0.23.jar" \
         ca.uqac.detection.Main

  Ou avec chemin explicite :
    java -cp "bin:lib/beepbeep-3.13.jar" ca.uqac.detection.Main /chemin/vers/log.txt [seuilRush]

  Fichiers produits (racine du projet PerforceLog/) :
    lib/beepbeep-3.13.jar         → dépendance BeepBeep 3.13
    log.txt                       → entrée (log brut Perforce)
    perforce_events_v3.json       → événements enrichis (export principal)
    perforce_events_v3.csv        → même schéma
    perforce_counters.json        → Counters OpenMetrics (_total)
    perforce_gauges.json          → métriques Gauge + série
    perforce_histogrammes.json    → buckets de durées
    perforce_summaries.json       → quantiles de durées
    perforce_events_alertes.json  → alertes phase 2
    figures/*.png               → 8 graphiques JFreeChart (paper)
